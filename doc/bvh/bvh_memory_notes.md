# BVH memory and traversal notes

Working notes for the BVH node memory, the triangle memory, and the traversal FSM. Offline reference;
`doc/craft_status.md` stays the source of truth for decisions.

## 1. Where the scene lives

Two options, same hardware underneath:

| | Scene fixed in the bitstream | Scene written by the PS |
|---|---|---|
| Storage | Block RAM (BRAM36) | Block RAM (BRAM36) |
| Read port (traversal) | Your RTL | Your RTL (identical) |
| Write port | Unused | AXI BRAM Controller in the block design (BD), driven by the ARM |
| Initial contents | `$readmemh` from a generated `.mem` | Same, plus the PS can overwrite between frames |
| Changing the scene | Re-synthesize and implement | Software only |

Plan: write the memory as your own inferred RAM module with a read port for traversal and a native write port
(`clk`, `en`, `we`, `addr`, `din`). For now nothing drives the write port and `$readmemh` sets the scene.
Later the BD connects an AXI BRAM Controller's `BRAM_PORTA` to it. Traversal RTL doesn't change.

- Off-chip DDR (512 MB on the PYNQ-Z2) is the other place a scene could go, but every node fetch would take
  tens of cycles in a pointer-chasing loop. On-chip BRAM is the right home at this scene size.
- Middle option, noted and skipped: `updatemem` patches BRAM contents into an existing bitstream without
  re-implementing. Fiddly with inferred RAMs.

## 2. BRAM facts (7-series, Zynq-7020)

- 140 BRAM36 on the chip (~4.9 Mb). Each BRAM36 can be used as two independent BRAM18s.
- BRAM36 port shapes:

| Mode | Widest port | Depth at that width |
|---|---|---|
| True dual-port (two read/write ports) | 36 bits | 1024 |
| Simple dual-port (one read-only + one write-only port) | 72 bits | 512 |

- Simple dual-port fits the plan: traversal reads, the PS (or nothing) writes. The cost: the PS can't read
  the scene back through BRAM.
- Every BRAM read goes through a register: data arrives at least 1 cycle after the address. An optional
  second register inside the BRAM (the output register, `DOB_REG`) makes it 2 cycles and is usually what
  you want at 125 MHz.

## 3. Node memory sizing (worked out)

Assumptions: n = 1024 triangles, one triangle per leaf, perfectly balanced binary tree.

- Interior nodes = n - 1 = **1023**. Each entry holds both children's boxes, so the FSM gets both in one fetch.
- Box = 6 coordinates x 28 bits (SQ11.16) = 168 bits. Entry = 2 boxes = **336 bits**.
- Total: 1023 x 336 = 343,728 bits.
- Simple dual-port: 5 wide (5 x 72 = 360 bits) x 2 deep (512 each) = **10 BRAM36**.
  True dual-port: 10 wide (10 x 36 = 360 bits) x 1 deep (1024) = **10 BRAM36**.
- 10 of 140 BRAM36 = ~7% of the block RAM.
- **24 spare bits per entry** (360 - 336), free in either layout.
- The width of one fetch sets the BRAM count, not the scene size. That's why a more compact box format
  could matter (see the open questions).

## 4. Inferring the BRAM in RTL

Same pattern as the existing lookup tables (`norm_lut` in `generate_ray_norm.sv`, `reciprocal_lut` in
`ray_dir_inverse.sv`), with these changes:

1. Attribute `(* ram_style = "block" *)` immediately before the declaration (the tables use
   `rom_style = "distributed"`).
2. Declaration: `logic` or an array of a packed node struct, unpacked depth, e.g. `node_t mem [1024];`.
3. **The read must be inside the clocked block:** `rd_data_q <= mem[rd_addr];`. A combinational read
   (`assign rd = mem[addr];`, as in the tables) can't go into a BRAM. Vivado warns and builds it from
   LUTRAM instead.
4. Optional second read register right after the first: Vivado puts it into the BRAM output register.
   Read latency becomes 2.
5. No reset on the array or on the read registers. A read enable such as `~ds_stall_i` is fine; BRAM
   has an enable pin.
6. Write port: separate clocked `if (we) mem[waddr] <= wdata;`. Single clock for now.
7. Init: `initial $readmemh("scene_nodes.mem", mem);` (any name; generated by a script, not hand-edited).
8. Make it a small parameterized module (data width, depth, init file). Node memory and triangle memory
   are two instances.

**Checking that it worked:**
- Synthesis log: "Block RAM: Preliminary Mapping Report" lists the array with its width and depth.
- Utilization: about 10 RAMB36 for the node memory (or the same in RAMB18 halves).
- No "trimmed" warnings on the memory. Bits that are never read get removed.

**Rebuild script:** a new module in `rtl/src/` and a generated `.mem` in `rtl/mem/` are globbed already;
a scene generator in `scripts/` needs nothing. Subfolders are NOT globbed. The BD + AXI BRAM Controller
step later is not covered by `create_project.tcl` yet.

## 5. Open questions to work through

Node layout:
1. With a perfectly balanced tree stored in a fixed order (level by level, root at index 0), does a node need
   to store where its children are? Could the FSM compute a child's index, whether a child is a leaf, and
   which triangle a leaf holds, from the current index alone?
2. What does insisting on a perfectly balanced tree cost? Look at how the C++ builder picks its splits, and
   picture a scene where most triangles sit in one small corner.
3. If the tree is not perfectly balanced, what must an entry hold besides the two boxes (child index,
   leaf flag, triangle start/count)? Does it fit in 24 spare bits?
4. Compact boxes (whole-number corners: min floored, max ceiled; boxes only grow): how many bits per
   coordinate? Does it change the BRAM count? What does `ray_bbox_intersect` need to accept them?

Triangle memory:
5. Repeat the sizing for triangles: 3 vertices x 3 x 28 bits, or another form (one vertex + two edges is
   common for the intersection test). Width per fetch -> BRAM count.

Traversal FSM:
6. Read latency (1 or 2 cycles) + `ray_bbox_intersect` latency (4) = cycles per node visit for one ray.
   What is the traversal rate, and can several rays share the loop to fill those cycles?
7. Which per-box values live only until that box's decision (the traversal stack)? How deep can the
   stack get for a balanced tree of 1024 leaves?
8. Later, with the PS on the write port: where does a second traversal lane read from? Compare how many
   full-width READ ports each layout gives: simple dual-port (5 x 72, 2 deep) vs true dual-port
   (10 x 36, 1 deep). Both cost 10 BRAM36 here.

PS as a second renderer (distant goal: dynamic work queue, PS and PL each take the next piece of the frame):
9. When the PS traces a pixel it walks the BVH thousands of times. Where should it read nodes from: a PL BRAM
   over the AXI general-purpose port (uncached, a bus round trip per access) or its own copy of the scene in
   DDR through its L1/L2 caches? What does that say about whether the PS needs a port on the node BRAM?
10. What is actually shared between PS and PL for the queue? (A "next work item" counter both sides take from
    without collisions: how big, where does it live, how is a take made atomic?)
11. Granularity: with a bus round trip per request, is the work item a pixel or a tile? How big a tile?
12. Matching output: the PS does its own math (float or fixed point?). Should its pixels be statistically
    indistinguishable from the PL's, and what would that take (same TEA hash per pixel/sample, same camera)?
13. Rough rates: how many rays per second might the two Cortex-A9 cores (650 MHz) manage vs the PL? Is the
    PS's share worth the complexity?

## 6. C++ reference

- `BVH::hit` in `bvh.inl` is the reference. It is not in this repo (`cpp/` has `bbox.h`, `triangle.h`,
  `scene.h`, ...); a copy lives outside it.
- Known bug: line 248 loops over all `primitives` at a leaf instead of `node.start .. node.start + node.size`.
  The image is correct but there's no BVH speedup.
- Things the traversal relies on (already established): every box test starts from times (-INF, INF);
  children are visited nearest entry first; the second child is skipped when its entry >= the closest
  primitive hit so far; `times.y` is never used. The closest-hit register is updated only by primitive hits.

## 7. Key facts from the vendor guides

Inference (from UG901, Vivado Synthesis):
- BRAM is inferred from an array whose read is synchronous: either the read data is registered
  (`q <= mem[addr]`) or the read address is registered and the array is read with it. A purely
  combinational read can only become LUTRAM.
- `ram_style` values on 7-series: `"block"`, `"distributed"` (LUTRAM), `"registers"` (flops). Without the
  attribute, Vivado picks by size; small arrays tend to become LUTRAM.
- `$readmemh` / `$readmemb` in an `initial` block is supported in synthesis for RAM and ROM contents.
  The `.mem` file must be in the project (`rtl/mem/*.mem` already is), the same way the existing tables work.
- A second register after the read register, with the same enable and no reset, is absorbed into the BRAM
  output register.
- Write modes (read-first, write-first, no-change) follow from how the RAM is coded. They only matter when
  a read and a write hit the same address in the same cycle. With the PS writing only while traversal is
  idle, that never happens; don't spend time on it now.
- Vivado splits a large array into BRAM36/BRAM18 pieces by itself (width first, then depth with an output
  mux). The `cascade_height` attribute can change the split; not needed now.

Hardware (from UG473, 7 Series Memory Resources, chapter 1):
- BRAM36 = 36 Kb. True dual-port widths: 1, 2, 4, 9, 18, 36 bits; simple dual-port adds 72 bits. A BRAM18 is
  half: up to 18 bits true dual-port, 36 bits simple dual-port.
- The 9/18/36/72-bit widths include parity bits (1 per byte). In an inferred RAM they're ordinary data bits,
  which is why 72 bits are usable, not 64.
- Read data appears after a clock edge (always registered). The optional output register (`DOA_REG` /
  `DOB_REG`) adds a cycle but greatly shortens the clock-to-out delay into the fabric. Expect to need it at
  125 MHz when the read data feeds logic directly.
- Each port has its own clock, enable, write enable (byte-wide on wide ports), and address. That byte-wide
  write enable is what the AXI BRAM Controller drives later.

For later (PS write port):
- The AXI BRAM Controller writes 32-bit words (configurable width, but nowhere near 360 bits). Either the
  RAM gets a narrow write port and a wide read port (asymmetric RAM, supported by inference; see UG901
  "Asymmetric RAMs"), or a small adapter collects words into a full entry before writing. Decide when the
  PS path is built.

Offline without the PDFs: Vivado Language Templates (Tools > Language Templates > SystemVerilog > Synthesis
Constructs > RAM), "Simple Dual Port, single clock". They show the exact coding shapes Vivado infers.
